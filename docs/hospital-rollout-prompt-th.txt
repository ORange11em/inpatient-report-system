ทำงานในโปรเจกต์ระบบรายงานผู้ป่วยในของโรงพยาบาล ระบบเดิมอยู่ใน inpatient (PHP/MySQL) ระบบใหม่อยู่ใน new-system (Next.js/FastAPI/PostgreSQL) เป้าหมายคือให้พยาบาลใช้ระบบใหม่ได้ครบวงจร เปิดดูรายงานย้อนหลังได้ และให้ฝ่ายไอทีมีหลักฐานตัดสินใจก่อนสลับระบบ

อ่าน AGENTS.md, new-system/docs/ui-progress.md, new-system/docs/parity-phase-5-import.md, new-system/docs/parity-phase-6-acceptance.md และ new-system/OPERATIONS_GUIDE_TH.md ก่อน ใช้ผลเดิมเป็นจุดเริ่มต้น ตรวจสถานะจากโค้ดและการรันจริง ทำงานทีละช่วงและลงมือทำส่วนที่ทำได้ในเครื่องทดสอบ ตามกติกา AGENTS.md หากต้องขยายขอบเขตไปแก้เครื่องมือนำเข้า โครงสร้างฐานข้อมูล สูตรรายงาน API หรือเพิ่ม dependency ให้ระบุไฟล์ เหตุผล และผลกระทบ แล้วขออนุมัติการเปลี่ยนแปลงนั้นก่อน งานนี้เริ่มจากเครื่องทดสอบแยก การนำเข้าฐานจริงหรือเปิดเว็บให้ใช้งานจริงต้องได้รับอนุมัติแยก

1. ตรวจว่ามีข้อมูลต้นทางให้ย้ายจริงเพียงใด
ตรวจสำเนาฐานเก่าที่ได้รับอนุญาตแบบอ่านอย่างเดียว รายงานจำนวนแถวของ data_all, data_confirm, data_split_patient, pressure, readmit และ tb_news พร้อมวันแรกและวันสุดท้ายสำหรับตารางที่มีวันที่ ตรวจหอและประเภทเวรที่จะใช้จับคู่ สำเนา inpatient/db/db_inpatient.sql ในโครงการเคยตรวจพบว่าทั้งหกตารางว่าง หากมีเพียงไฟล์นี้ ให้เตรียมคำสั่งอ่านยอดสำหรับฝ่ายไอทีและระบุไฟล์ส่งออกที่ยังขาด ให้รับไฟล์ผ่านพื้นที่จำกัดสิทธิ์ของโรงพยาบาล เก็บรหัสผ่านและข้อมูลระบุตัวผู้ป่วยออกจากแชต ซอร์ส และบันทึกผล ระหว่างรอให้ซ้อมด้วยข้อมูลสมมติที่ติดป้ายชัดเจน

2. พัฒนาและซ้อมการนำเข้าในฐานทดสอบ
ตรวจแล้วใช้เครื่องมือ data_all และ data_confirm ที่มีอยู่ต่อ เสนอส่วนเพิ่มสำหรับข้อมูลแยกสาขา แผลกดทับ การกลับมารักษาซ้ำ และข่าว ให้ตัวนำเข้ารับรูปแบบไฟล์ที่ตกลงกับฝ่ายไอที ระบุวิธีจับคู่หอ เวร วันที่ และบัญชีผู้ยืนยันโดยคงความหมายของประวัติเดิม เก็บค่าว่างแยกจากศูนย์ แยกแถวที่จับคู่ไม่ได้พร้อมเหตุผล ห้ามสร้างผู้ยืนยันหรือเวลาแทนข้อมูลที่หายและห้ามย้ายรหัสผ่านเดิม
ให้แสดงผลคาดการณ์ก่อนเขียน (dry-run) สำรองฐานทดสอบก่อนนำเข้า และทดสอบว่ารันไฟล์เดิมซ้ำแล้วไม่สร้างรายการเพิ่ม ตรวจว่าข้อมูลในแต่ละชุดเชื่อมกลับไปที่หอ วัน และเวรที่ถูกต้อง กระทบยอดแถวต้นทางกับจำนวนที่นำเข้า ข้าม หรือมีปัญหาโดยอธิบายได้ทุกแถว แล้วเทียบยอดก่อนและหลังรายหอ/วัน/เวร รวมถึงรายเดือนตามลักษณะข้อมูล เปิดรายงานจากข้อมูลที่นำเข้าผ่านหน้าเว็บจริงและแนบเฉพาะผลรวมที่เปิดเผยได้

3. ปิดข้อค้างที่มีผลต่อการใช้งานของหอผู้ป่วย
รันทดสอบรายงานรวมทุกตึกที่เคยคาด 12 แต่ได้ 24 ในฐานที่แยกไว้ หาสาเหตุและตรวจค่าคาดหวังกับหลักฐานก่อนแก้ ตรวจอัตราครองเตียงเมื่อจำนวนเตียงเปลี่ยน ยอดรวมอัตราหมุนเวียนเตียง และใบพิมพ์ Productivity เทียบระบบเดิมหรือผลคาดหวังที่เจ้าของรายงานรับรอง ส่งความต่างที่ยังตัดสินไม่ได้ให้ผู้รับผิดชอบรายงาน
ทดสอบด้วยบัญชีสมมติตามสิทธิ์ ตั้งแต่เข้าสู่ระบบ เลือกหอและเวร บันทึก ยืนยัน ส่งกลับ แก้ไข ดูประวัติ พิมพ์ และส่งออก ตรวจว่าผู้ใช้เข้าถึงได้ตามหอที่ได้รับมอบหมาย ทวนข้อค้าง UI และทดสอบหน้าที่เกี่ยวข้องที่ 360/768/1024/1440px รันชุดทดสอบหน้าบ้าน หลังบ้าน lint, typecheck และ build บันทึกคำสั่งและผลจริง

4. เตรียมส่งให้โรงพยาบาลตรวจรับ
ตรวจว่าเครื่องเป้าหมายรันทั้ง Next.js, FastAPI และ PostgreSQL ได้ ยืนยันกับฝ่ายไอทีว่าจะให้เข้าเฉพาะเครือข่ายโรงพยาบาลหรือจากภายนอก จัดทำวิธีติดตั้งตามเครื่องจริง รวม HTTPS การตั้งค่าความลับและสิทธิ์ การสำรอง การเฝ้าระวัง และผู้รับผิดชอบ ทดลองกู้คืนลงฐานแยกและเปิดรายงานจากฐานที่กู้ได้ ซ้อมการสลับระบบ ระบุจุดหยุดกรอกในระบบเดิม วิธีนำเข้ารายการที่เพิ่มหลังซ้อม วิธีจัดการรายการที่กรอกหลังสลับหากต้องย้อนกลับ และผู้ตัดสินใจย้อนกลับ ให้พยาบาลและหัวหน้าหอตรวจรับงานประจำเวร ฝ่ายรายงานรับรองตัวเลข และฝ่ายไอทีตรวจรับการติดตั้งและการกู้คืน

อัปเดต new-system/docs/ui-progress.md หลังจบแต่ละช่วง สรุปเป็นภาษาไทยว่าอะไรผ่านแล้วด้วยข้อมูลสมมติ อะไรยืนยันแล้วด้วยสำเนาที่ได้รับอนุญาต และอะไรยังรอข้อมูลหรือการตัดสินใจ ให้สรุปว่าพร้อมใช้งานจริงได้เมื่อยอดข้อมูลตรวจสอบได้ ความต่างของรายงานได้รับการรับรอง การกู้คืนผ่าน และผู้รับผิดชอบของโรงพยาบาลตรวจรับแล้ว
