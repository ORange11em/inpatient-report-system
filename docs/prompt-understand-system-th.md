# Prompt: ทำความเข้าใจโครงสร้างทั้งหมดของระบบรายงานผู้ป่วยใน

> วิธีใช้: คัดลอกข้อความใต้เส้นคั่น ไปวางเป็นข้อความแรกของบทสนทนาใหม่ (แนบ workspace หรือเปิดโปรเจกต์นี้ให้โมเดลเข้าถึงไฟล์) แล้วจึงสั่งงานต่อในเทิร์นถัดไป

---

## บทบาทและเป้าหมาย

คุณคือวิศวกรซอฟต์แวร์ที่ต้อง **ทำความเข้าใจโครงสร้างทั้งหมด (whole-system understanding)** ของโปรเจกต์นี้ก่อนลงมือแก้ไขใด ๆ เป้าหมายไม่ใช่การแก้โค้ด แต่คือการสร้าง "แผนที่ระบบ" ที่ถูกต้อง ตรวจสอบได้จากซอร์สจริง และเพียงพอให้ทีมตัดสินใจงานเฟสถัดไปได้

ระบบคือ **ระบบรายงานจำนวนผู้ป่วยในของโรงพยาบาล** ผู้ใช้หลักคือพยาบาลผู้บันทึกข้อมูลประจำหอ หัวหน้าหอผู้ป่วย ผู้ดูรายงาน และผู้ดูแลระบบ ระบบใหม่อยู่ระหว่างการย้ายจากระบบเดิมที่เขียนด้วย PHP + MySQL โดยยึดพฤติกรรมของระบบเดิมเป็นข้อกำหนดหลัก

## แหล่งความจริงและลำดับความสำคัญ

อ่านตามลำดับนี้ และถือว่าไฟล์โค้ดจริงมีน้ำหนักเหนือเอกสารเสมอ หากเอกสารกับโค้ดขัดกันให้รายงานความขัดแย้งนั้น ห้ามเลือกข้างเองโดยไม่แจ้ง

1. `AGENTS.md` (รากโปรเจกต์) และ `new-system/frontend/AGENTS.md` — กติกาและข้อจำกัดของงาน
2. `new-system/docs/ui-spec.md`, `new-system/docs/ui-progress.md` — ขอบเขตงาน UX/UI และสถานะปัจจุบัน
3. `new-system/docs/system-architecture-and-flow.md` — สถาปัตยกรรมและ mapping เก่า → ใหม่ (ใช้เป็นแผนที่ตั้งต้น แล้วตรวจยืนยันกับโค้ด)
4. `new-system/docs/parity-*.md`, `new-system/INPATIENT_PARITY_TH.md`, `new-system/OPERATIONS_GUIDE_TH.md` — ผลตรวจเทียบระบบเดิมและคู่มือปฏิบัติงาน
5. โค้ดจริง: `new-system/frontend/`, `new-system/backend/`
6. ระบบเดิม (อ่านอย่างเดียว ห้ามแก้): `inpatient/`

## ลำดับการสำรวจที่ต้องการ

ทำตามลำดับนี้ทีละชั้น แล้วสรุปเป็นชั้น ๆ ก่อนไปชั้นถัดไป

1. **ภาพรวมสถาปัตยกรรม** — frontend, backend, ฐานข้อมูล, ชั้น proxy/rewrite, สภาพแวดล้อม dev/prod และจุดที่ระบบใหม่ยังพึ่งระบบเดิม
2. **Frontend** — routing ทั้งหมดใน `app/`, shared components, `lib/` (helper โดเมน), design tokens, การจัดการ state/session, การเรียก API ผ่าน `lib/api.js` และ rewrite ใน `next.config.mjs`
3. **Backend** — จุดเข้า `main.py`, router/endpoint ทั้งหมดใน `api.py` (method, path, สิทธิ์, CSRF), `schemas.py`, `models.py`, `permissions.py`, `security.py`, `reports.py`, `occupancy.py`
4. **Data model** — ตารางทั้งหมด, PK/FK/unique/check ที่สำคัญ, migration `alembic/versions/` เรียงตามเลข, seed ข้อมูลตั้งต้น, ตาราง tracking การนำเข้า
5. **Mapping เก่า → ใหม่** — ไฟล์ PHP แต่ละไฟล์ไปลงเอยที่ route/endpoint/ตารางใด และไฟล์ใดไม่ถูกย้ายพร้อมเหตุผล
6. **เส้นทางการทำงานหลัก (end-to-end)** — login → เลือกหอ → บันทึกเวร → ยืนยัน → ส่งกลับแก้ไข → ดูประวัติ; และเส้นทางตัวชี้วัด, ข่าวประกาศ, รายงาน 15 ชนิด (จอ/พิมพ์/Excel), การนำเข้าข้อมูลเดิม
7. **สิทธิ์และขอบเขตข้อมูล** — บทบาท global vs ต่อหอ, จุดบังคับสิทธิ์ทุกชั้น, พฤติกรรมของ `auditor` ตามโค้ดจริง
8. **การทดสอบและปฏิบัติการ** — ชุดทดสอบฝั่ง frontend/backend, วิธีรัน, ตัวแปรสภาพแวดล้อมที่ต้องมี (บอกแค่ชื่อ ห้ามอ่านค่าจากไฟล์ env), CLI scripts
9. **จุดเสี่ยงและหนี้ทางเทคนิค** — โค้ดที่ตายแล้ว, เอกสารที่ล้าสมัย, ความต่างที่ตั้งใจจากระบบเดิม, ช่องว่างที่ยังพิสูจน์ไม่ได้

## สิ่งที่ต้องส่งมอบ

ตอบเป็นภาษาไทยด้วยโครงสร้างต่อไปนี้

1. **สรุปผู้บริหาร 10–15 บรรทัด** — ระบบนี้ทำอะไร แยกเป็นกี่ชั้น อะไรคือแหล่งข้อมูลจริง
2. **แผนผังระบบแบบข้อความ** — กล่อง/ลูกศรแสดง frontend → proxy → backend → DB และจุดเชื่อมกับระบบเดิม
3. **ตารางองค์ประกอบหลัก** — ชื่อส่วน / ไฟล์รับผิดชอบ / หน้าที่ / ใครเรียกใช้
4. **ตาราง route ↔ endpoint ↔ ตารางฐานข้อมูล ↔ ไฟล์ PHP เดิม**
5. **ลำดับงานหลัก 2–3 เส้น** พร้อมระบุไฟล์และฟังก์ชันในแต่ละขั้น
6. **ตารางสิทธิ์** — บทบาท × การกระทำ × ผลลัพธ์เมื่อไม่มีสิทธิ์ (รหัส error)
7. **รายการสิ่งที่ยังไม่ชัด/ขัดแย้ง** — พร้อมหลักฐานและคำถามที่ต้องถามเจ้าของงาน
8. **แผนอ่านต่อสำหรับคนใหม่** — ลำดับไฟล์ 8–12 ไฟล์ที่ควรอ่านก่อนแก้เฟสถัดไป พร้อมเหตุผลหนึ่งบรรทัดต่อไฟล์
9. **คำศัพท์เฉพาะของโปรเจกต์** — คำไทยที่ใช้บนจอเทียบกับชื่อในโค้ด

## กติกาการตอบ

- **อ่านโค้ดจริงก่อนสรุป** ทุกข้อกล่าวอ้างต้องอ้างอิงตำแหน่งได้ในรูปแบบ `path/file.ext:line` หรือชื่อฟังก์ชัน/ตาราง
- **แยกประเภทข้อความให้ชัด**: `ยืนยันจากโค้ด` / `ยืนยันจากเอกสาร` / `อนุมาน (ยังไม่ยืนยัน)` — ห้ามทำให้ข้อสันนิษฐานดูเหมือนข้อเท็จจริง
- **ห้ามแก้ไฟล์ใด ๆ** ในเทิร์นนี้ เป็นงานอ่านและสรุปเท่านั้น ถ้าพบว่าต้องแก้ ให้เสนอเป็นรายการแยก
- **ห้ามเปิดเผยความลับ** — ห้ามอ่านหรือพิมพ์ค่าใน `.env*`, `connect.php`, รหัสผ่าน, token, ข้อมูลผู้ป่วยจริง ระบุได้แค่ชื่อตัวแปร
- ระบบเดิม `inpatient/` เป็นแบบอ่านอย่างเดียว และพฤติกรรมของมันคือข้อกำหนดของระบบใหม่
- วันที่บนจอเป็น พ.ศ. ผ่าน util กลาง (`lib/thai-date.mjs`) ค่าที่ส่ง API เป็น ISO `YYYY-MM-DD` — ตรวจว่ากฎนี้ถูกทำจริงทุกจุด
- ข้อความบนจอเป็นภาษาไทยตามคำศัพท์ใน spec ห้ามใช้ศัพท์ระบบ เช่น API, payload
- ถ้าพบว่าเอกสาร (`docs/*.md`) ขัดกับโค้ด ให้ยกมาทั้งคู่แล้วถามก่อนสรุป
- ถ้าข้อมูลไม่พอสำหรับสรุป ให้บอกว่าขาดอะไรและต้องอ่านไฟล์ใดต่อ อย่าเดา
- ตอบกระชับ ใช้ตารางเมื่อเปรียบเทียบ และไม่ต้องวางโค้ดยาว ยกเว้น snippet 3–10 บรรทัดที่จำเป็นต่อการอธิบาย

## เกณฑ์ว่าคำตอบ "ครบ"

- ระบุได้ว่าผู้ใช้แต่ละบทบาททำอะไรได้/ไม่ได้ และโค้ดบังคับที่บรรทัดใด
- อธิบายได้ว่าข้อมูลหนึ่งแถวของ "การบันทึกเวร" ไหลจากฟอร์มไปถึงตารางใด ผ่าน endpoint ใด และถูกตรวจอะไรบ้าง
- บอกได้ว่ารายงานแต่ละชนิดคำนวณที่ไฟล์ใด และทำไมผลจอ/พิมพ์/Excel อาจต่างกัน
- ระบุได้ชัดว่าส่วนใดของระบบเดิมยังไม่ถูกย้าย และส่วนใดต่างโดยตั้งใจ
- มีรายการคำถามที่ยังค้างพร้อมผู้ตัดสินใจ

เริ่มจากอ่าน `AGENTS.md` และ `new-system/docs/system-architecture-and-flow.md` แล้วตรวจยืนยันกับโค้ดจริงก่อนตอบ

> ช่วยสร้างแผนที่โครงสร้างทั้งหมดของโปรเจกต์นี้ (ระบบรายงานผู้ป่วยใน: Next.js App Router + FastAPI + PostgreSQL, มีระบบเดิม PHP/MySQL อยู่ที่ `inpatient/` แบบอ่านอย่างเดียว) โดยอ่านโค้ดจริงใน `new-system/frontend/`, `new-system/backend/` และเอกสาร `new-system/docs/system-architecture-and-flow.md`, `ui-spec.md`, `ui-progress.md`, `parity-*.md` แล้วสรุปเป็นภาษาไทย: (1) แผนผังสถาปัตยกรรมและชั้นการทำงาน (2) ตาราง route ↔ API endpoint ↔ ตาราง DB ↔ ไฟล์ PHP เดิม (3) เส้นทางหลัก login → บันทึกเวร → ยืนยัน → ส่งกลับ → รายงาน (4) ตารางสิทธิ์ 4 บทบาทพร้อมจุดบังคับสิทธิ์ (5) รายการเอกสาร/โค้ดที่ขัดกันหรือล้าสมัยพร้อม `path:line` (6) คำถามที่ยังต้องตัดสินใจ ห้ามแก้ไฟล์ ห้ามอ่านค่าความลับใน `.env*` หรือ `connect.php` และต้องระบุว่าข้อใดยืนยันจากโค้ด ข้อใดอนุมาน
