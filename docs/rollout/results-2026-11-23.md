# ผลตรวจและซ้อม 23 พฤศจิกายน 2569

ผลนี้ใช้ข้อมูลสมมติเท่านั้น ยกเว้นการอ่านโครงสร้าง/ส่วน Records ของ SQL dump ที่ได้รับ ไม่มีการเชื่อมฐานโรงพยาบาล ไม่มีการนำเข้าข้อมูลจริง และไม่มีการสลับระบบ

## 1. ตรวจสำเนาเก่าแบบอ่านอย่างเดียว

ไฟล์ `inpatient/db/db_inpatient.sql` SHA-256 `6178c0fbeefdffc02dc3d00b5b7bb457900d9f1c5308945cedee9106ba1da78c` มีส่วน Records ว่างของ `data_all`, `data_confirm`, `data_split_patient`, `pressure`, `readmit`, `tb_news`: 0 แถวทุกตาราง วันแรก/สุดท้ายไม่มีข้อมูล ไม่ใช่วันที่สร้าง dump มีหอ 19 แถว เวร 3 แถว (1 ดึก/2 เช้า/3 บ่าย) เดือน 12 แถว ไม่คัดลอกหรือย้ายบัญชี/รหัสผ่าน

[source-inventory.json](source-inventory.json) บันทึกวิธีตรวจและผล; จำนวนบนเซิร์ฟเวอร์จริงและช่วงข้อมูลจริงยังไม่ทราบ [source-inventory.sql](source-inventory.sql) พร้อมให้ฝ่ายไอทีตรวจฐานสำเนาแบบอ่านอย่างเดียว ผ่านการรัน SELECT ทั้ง 20 คำสั่งกับ MariaDB 10.4.32 ฐานว่างที่สร้างใหม่เฉพาะการทดสอบ ไม่ใช่การรับรองผลบน MySQL ของโรงพยาบาล ดู [inventory-sql-check.json](inventory-sql-check.json)

## 2. ซ้อมตัวนำเข้าเดิมโดยไม่แก้ตัวนำเข้าหรือโครงสร้าง

หลักฐาน [rehearsal-result.json](rehearsal-result.json) รวมแถวต้นทาง = นำเข้า+ข้าม+ผิด สำหรับทั้งไฟล์ปกติและไฟล์ข้อผิดพลาด ตารางเสริม 4 ตารางยังไม่มีตัวนำเข้า ไม่ได้ซ้อมด้วยการเขียนตรงแล้วเรียกว่านำเข้าผ่าน

## 3. สาเหตุรายงาน 24 แทน 12

อ่าน `backend/app/reports.py` พบว่า daily-all คืนแถวรายละเอียดตามหอและแถว “รวมทุกหอที่เลือก” อีกแถวหนึ่ง ชุด P1 วันที่ 1 พ.ย. 2569 เวรดึกของหอ A มี PT คงเหลือ `10+2+1−1=12` หอ B `6+1−1=6`

| สิทธิ์ที่ใช้ | ผลรวมเฉพาะรายละเอียด | แถวรวม | บวกทุกแถวแบบข้อผิดพลาดเดิม |
|---|---:|---:|---:|
| ดูหอ A | 12 | 12 | 24 |
| ผู้ดูแลเห็น A+B | 18 | 18 | 36 |

ตรวจผ่าน HTTP ทั้งฐานนำเข้าและฐานกู้คืน และตรวจหน้าเว็บ/ไฟล์ XML ซ้ำได้ 12/18 เหมือนกัน จึงยืนยันได้ว่าความต่างกรณีนี้เกิดจากการรวมแถวสรุปซ้ำในวิธีตรวจเดิม ไม่มีเหตุให้แก้สูตรหรือเพิ่มค่าคาดหวังเป็น 24

ไฟล์ทดสอบเดิม `run_daily_workflow.py` มี assertion แยกรายละเอียดกับ grand total อยู่แล้วก่อนงานนี้ (ตรงกับบันทึกเฟส 6); รันซ้ำผ่าน 657 ข้อ โดยไม่แก้ไฟล์นั้นหรือสูตร ตัวเลขนี้ยังไม่แทนการรับรองรายงานจากเจ้าของรายงานโรงพยาบาล

## 4. กู้คืนและย้อน snapshot ในฐานแยก

สำรองหลังนำเข้าและกรณีเตียงว่าง กู้ลง `rollout_recovery` ที่สร้างใหม่ ผ่านการเทียบทุกแถวของรายการเวรพร้อม mapping หอ/เวร/สถานะ/ตัวนับ และจำนวน crosswalk/events/history/issues/batches กับฐานต้นฉบับ: daily entries 14, crosswalk 14, submission events 14, history 3, issues 2, batches 6 จากนั้นเริ่มบริการชี้ฐานกู้คืนและเข้าสู่เว็บดูรายงาน/พิมพ์/ส่งออกได้ตรงเดิม ใช้เวลาประมาณ 9.14 วินาทีสำหรับ restore และตรวจ HTTP/browser ของชุดเล็กนี้ ไม่ใช่เวลารับรองการกู้คืนข้อมูลจริงหรือ RTO โรงพยาบาล

กู้ snapshot ก่อนนำเข้าไป `rollout_rollback` อีกฐานหนึ่ง จำนวนตารางธุรกรรมทั้ง 6 กลับเป็น 0 โดยไม่ restore ทับฐานต้นฉบับ ไม่ได้ซ้อมนำรายการกรอกหลังสลับกลับ PHP/MySQL หรือสลับผู้ใช้งานจริง ดูจุดหยุด/การเก็บรายการเพิ่ม/ผู้ตัดสินใจที่ยังต้องตกลงใน [แผนตรวจรับ](README.md#จุดหยุดและการตรวจรับก่อนเปิดจริง)

## 6. ตรวจรายการแก้ไขและงานที่ยังรอ

ไม่มี Git repository จึงตรวจ SHA-256 กับ snapshot ก่อนงานแทน พบซอร์สเดิมที่ป้องกัน 172 ไฟล์ใน `inpatient`, backend app/migrations และ frontend app/components/lib เหมือนเดิมทั้งหมด รวมถึงตัวนำเข้า สูตร API model และ `run_daily_workflow.py` ไม่แก้ dependency/config/AGENTS.md ไม่ลบไฟล์ มีเฉพาะเอกสาร ชุดทดสอบใหม่ และผลทดสอบที่สร้างใหม่ใน docs/screenshots/output ดู [change-review.json](change-review.json)

ยังรอ: สำเนาที่มีข้อมูลและ manifest จากฝ่ายไอที; การตกลงรูปแบบ/อนุมัติตัวนำเข้าเสริม 4 ตาราง; การรับรอง Turnover รวม/ครองเตียงเมื่อเตียงแปรผัน/Productivity ใบพิมพ์; ข้อค้าง UI F01/F03/F04; การตรวจรับโดยพยาบาล/หัวหน้าหอ; รายละเอียดเซิร์ฟเวอร์/เครือข่าย/HTTPS/ผู้รับผิดชอบและแผนย้อนรายการหลังสลับจริง การทดสอบรอบนี้ไม่ปิดข้อค้างเหล่านี้

พร้อมให้ทดลองตรวจรับด้วยข้อมูลสมมติในฐานแยก ยังไม่พร้อมเปิดใช้จริงจนกว่าจะยืนยันยอดข้อมูลจริง รับรองความต่างรายงาน ซ้อมกู้คืนบนเครื่องเป้าหมาย และได้รับอนุมัติจากผู้รับผิดชอบของโรงพยาบาลครบถ้วน
