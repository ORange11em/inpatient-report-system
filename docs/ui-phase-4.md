# เฟส 4 — ประวัติและรอยืนยัน

อัปเดต 19 พฤศจิกายน 2569 ทำเฉพาะหน้าประวัติ `/history` และรอยืนยัน `/history?status=unconfirmed` พร้อมองค์ประกอบร่วมที่ต้องใช้ ไม่เริ่มเฟส 5–7

## ขอบเขตที่ตกลงและพฤติกรรมเดิม

เมื่อถามเรื่องค่าเริ่มต้น 7 วันและการโหลดทันที ผู้ใช้ตอบว่า **“เอาตามระบบเดิมอะแล้วแต่เลย”** จึงคงประวัติเป็นช่วงต้นเดือนถึงวันนี้และกดค้นหาเอง ส่วนลิงก์รอยืนยันยังโหลด `unconfirmed` ทุกช่วงวันอัตโนมัติตามเดิม นี่เป็นข้อยกเว้นจากค่าเริ่มต้น 7 วันใน C3 ตามคำตอบครั้งนี้ ผู้ใช้ยังเลือกช่วงด่วน 7 วัน/เดือนนี้/เดือนก่อนในตัวกรองได้เอง

คงสิทธิ์เดิม: ผู้มี `ward.can_write` แก้ไขและยืนยันรายการที่ยังไม่ยืนยันได้ ผู้ดูแลระบบส่งกลับรายการที่ยืนยันแล้วได้ บัญชีอ่านอย่างเดียวเปิดดูได้ ไม่มีการสร้างบทบาทหัวหน้าหอหรือกฎสิทธิ์ใหม่

ภาพ `03-history.png` ไม่พบตอนเริ่ม จึงตรวจจากภาพเดิม `Screenshot 2026-11-19 144406.png` และทำสำเนาเป็น [03-history.png](screenshots/03-history.png) เก็บต้นฉบับไว้ครบ

## หน้าจอที่เปลี่ยน

- ใช้ PageHeader ตามชื่อเมนูจริง: “ตรวจสอบและยืนยันข้อมูล” และ “รอยืนยันการส่งข้อมูล”
- FilterBar มีหอผู้ป่วย ช่วงวันที่แบบ พ.ศ. และสถานะ ในแถวเดียวเมื่อพื้นที่พอ มือถือเปิด BottomSheet ช่วงวันที่มีตัวเลือกด่วนใน dialog โดยยังค้นหาเมื่อกดปุ่ม
- ตัวกรองที่ใช้จริงแสดงเป็น chip และ sync query โดยคง path `/history`; ขณะเปลี่ยนตัวเลือกแต่ยังไม่ค้นหา จะแจ้งว่าผลลัพธ์ยังเป็นชุดก่อนหน้า
- ตารางบนจอกว้างมีหัวและคอลัมน์วันที่ค้าง เลื่อนแนวนอนได้เฉพาะกรอบตาราง บนมือถือใช้การ์ดและสลับมุมมองตารางได้ ปุ่มสลับเพียงชุดเดียวควบคุมทุกกลุ่มวันที่
- รอยืนยันจัดกลุ่มตามวัน โดยรักษาลำดับรายการที่บริการส่ง ไม่เรียงใหม่เฉพาะหน้าจนทำให้ pagination ผิดความหมาย
- แสดงวัน/เวลาแก้ไขจริงผ่าน util กลาง ส่วนชื่อผู้บันทึก/ผู้ยืนยันที่ข้อมูลตอบกลับไม่มีไม่สร้างขึ้นเอง
- ตารางระบุ **คงเหลือ PT/NB หลังรับ–จำหน่าย ไม่รวม A&D** ตามสูตรที่ยืนยันไว้ รายละเอียดมี “ยกมา” แยกต่างหาก ค่าที่เก็บและค่าที่เปิดในฟอร์มไม่ถูกเปลี่ยนจากการคำนวณแสดงผลนี้
- มี skeleton, error/retry, empty state และปุ่มล้างตัวกรอง/ดู 30 วันล่าสุดตามบริบท รอยืนยันที่ว่างใช้ข้อความเชิงบวกและ badge 0 ซ่อนตามเดิม

## ปุ่มแก้ไขเชื่อมฟอร์มเฟส 3

ใช้ `/entries?ward={row.ward_id}&date={row.service_date}&shift={row.shift_type_id}` เหมือนเดิม โดยใช้วัน ISO และ **primary key** ของเวร ไม่ใช้ legacy code, วันที่ปัจจุบัน หรือหอที่จำไว้แทนข้อมูลของรายการ

ทดสอบคลิกจริงจากประวัติไปฟอร์มด้วยหอ `example-b` ที่ไม่ใช่หอแรก วันที่ย้อนหลัง `2026-10-31` และเวร primary key `73` ซึ่งจับคู่ legacy `3`:

- URL และ `GET /entry-form` มีหอ/วัน/เวรตรงรายการ
- หัวและตัวเลือกหอแสดงหอ ข / เวรบ่าย / 31 ตุลาคม 2569
- ฟอร์มเฟส 3 เปิดรายการเดิม มี input 59 ตัว และ `pt_on=17` จากรายการ ไม่ใช่ยอดตั้งต้นสำรอง 99 ใน fixture
- รายการยืนยันแล้วและบัญชีอ่านอย่างเดียวใช้ “เปิดดู” พร้อมไอคอนกุญแจ แทนคำว่าแก้ไข โดยฟอร์มยังบังคับสิทธิ์เดิมของตน

## ยืนยันและส่งกลับ

“ตรวจสอบ” เปิดรายละเอียดจากข้อมูลรายการที่อ่านมาแล้ว ไม่เพิ่ม GET รายละเอียดซ้ำ ปุ่มยืนยัน/ส่งกลับปรากฏตามสิทธิ์เดิม และเปิด ConfirmDialog หรือ dialog ระบุเหตุผลก่อนส่งคำขอ

| คำขอ | ข้อมูลส่งที่คงเดิม |
| --- | --- |
| `POST /entries/{id}/confirm` | `{ expected_version: row.version }` และ CSRF เดิม |
| `POST /entries/{id}/return` | `{ expected_version: row.version, reason }` และ CSRF เดิม; trim เหตุผลก่อนส่ง |
| อ่านรายการ | `GET /entries` ด้วยตัวกรองเดิม + `offset = page × 50`, `limit = 51` |

เหตุผล required และยาวไม่เกิน 1000 ตาม `ReturnRequest` เดิม กรณีข้อมูลชนกัน dialog แสดงข้อผิดพลาดและเก็บเหตุผลที่พิมพ์ไว้ ผู้ใช้เลือกอ่านรายการล่าสุดแล้วตรวจใหม่ก่อนส่ง ไม่มีการ retry คำขอเขียนอัตโนมัติ

หลังสำเร็จยังส่ง event `inpatient-entries-changed`, อ่านหน้าปัจจุบันซ้ำ และย้อนหน้าก่อนหน้าเมื่อทำรายการกับแถวสุดท้ายของหน้าที่มากกว่า 1 ตามโค้ดเดิม พร้อม Toast และคืนโฟกัสไปผลการค้นหา

จับคำขอก่อน/หลังจริงจาก browser ด้วยข้อมูลสมมติ ทั้ง GET ที่ใช้ในสอง flow และ POST ยืนยัน/ส่งกลับตรงกัน รวม version, เหตุผลที่ trim และ CSRF ดู [ผลเทียบคำขอ](screenshots/phase-4/request-comparison.json) และ [hash ส่วนอ่าน/เขียน/ย้อนหน้า](screenshots/phase-4/protected-source.json)

## จำนวนรายการและสถานะ

บริการส่งเพียงรายการหนึ่งหน้าพร้อมแถวสำหรับตรวจหน้าถัดไป จึงแสดงจำนวนในชิปเป็น **“เฉพาะรายการในหน้านี้”** และนับจาก 50 แถวที่แสดง ไม่รวมแถวที่ 51 และไม่อ้างว่าเป็นยอดรวมทุกหน้า ส่วน badge เมนูยังมาจาก pending-count เดิมตามสิทธิ์ทุกช่วงวัน

ไม่มี persisted status “ยังไม่บันทึก” จึงไม่สร้างชิป 0 หรือส่ง `unrecorded` ไปค้น ให้ลิงก์ไปตรวจเวรที่ยังไม่บันทึกในหน้าแรกแทน ไม่มี bulk endpoint/คิวส่งไม่สำเร็จ จึงไม่เพิ่มยืนยันหลายรายการหรือปุ่มส่งซ้ำที่ไม่ตรงความหมายระบบ

- UI kit ที่ 360/768/1024/1440px ไม่มี page overflow และ DataTable แบบเดิมยังสลับการ์ด/ตารางได้
- `npm run build` ผ่าน; `npm run lint` ยังไม่มี script เดิม; `npx --no-install tsc --noEmit` ยังไม่มี compiler/config เดิม ไม่ติดตั้ง dependency เพิ่ม
